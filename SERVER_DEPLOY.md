# Запуск на сервере

Архив подготовлен для запуска текущей версии приложения. Файл `.env` включен в архив и содержит рабочие настройки и ключи.

## Требования

- Node.js 20 или новее
- PostgreSQL, если `POSTGRES_ENABLED=true`
- ffmpeg в `PATH`
- Python с установленным пакетом `gigaam`
- SMTP-доступ для email-отчётов, если включена отправка отчётов

## Быстрый старт

```bash
npm ci
python -m pip install gigaam
npm start
```

По умолчанию приложение слушает порт из `.env` (`PORT`). После запуска откройте:

```text
http://SERVER_IP:PORT/
```

Для расписаний действий задайте локальный часовой пояс и интервал проверки:

```env
TZ=Asia/Yekaterinburg
ACTION_SCHEDULER_INTERVAL_SECONDS=30
ACTION_SCHEDULER_RETRY_MAX_AGE_HOURS=168
```

Действия в режимах `daily` и `weekly` запускаются сервером после окончания выбранного периода группы. Дневные отчёты отправляются отдельно для каждого дня; в режиме `вчера` понедельник использует пятницу, если выходные отключены. Недельный отчёт охватывает понедельник–пятницу и отправляется после 18:00 пятницы (либо после окончания ночного пятничного интервала); суббота используется как окно догоняющей отправки. Обработку дневных записей по субботам и воскресеньям можно включить отдельной галочкой в действии. Неудачные периоды повторяются с задержкой и сохраняются для фонового повтора после смены даты; сбой отдельного файла не отменяет обработку остальных записей.

Ручная кнопка `Запустить` для планового действия и любого действия Google Диска, включая разовое `once`, только ставит задачу в серверную очередь. Обработка продолжает работать при закрытой странице, а параллельный дубль уже выполняющегося периода не создаётся. Разовые email-действия по-прежнему требуют открытой страницы. Свежие завершённые периоды имеют приоритет перед старыми повторами; предварительная почасовая загрузка архива не включена.

## Google Диск: локальная очередь и восстановление

Для фоновой работы должны быть доступны PostgreSQL и включён планировщик. Учётные данные Google задаются в `.env` согласно разделу Google Диска в `README.md`. Приложение сначала получает и транскрибирует записи, проверяет полноту каждой камеры, сохраняет готовый результат локально и только затем передаёт его независимой очереди доставки. Сбой авторизации, DNS или сети Google не должен останавливать обработку остальных камер.

Готовые результаты и подтверждения доставки хранятся в `.runtime/drive-outbox` относительно каталога приложения. Это постоянные JSON-записи, а не временные аудиофайлы: в них находятся транскрипт, параметры формирования TXT, состояние отправки и ID подтверждённого файла Google Диска. Дайте пользователю службы права чтения и записи на этот каталог, сохраняйте его при обновлении приложения и включите в резервное копирование вместе с PostgreSQL. Не очищайте его вместе с временным кэшем. Каталог содержит разговоры; ограничьте права доступа и не публикуйте его в Git или общедоступных архивах.

После перезапуска готовая локальная камера или камера с подтверждённой доставкой пропускается до обращения к архиву и загрузки блочного кэша. Неотправленный готовый TXT повторяется отдельной очередью с задержкой от 1 до 60 минут, без повторной транскрибации. Карточка показывает число локально готовых файлов, ожидающих отправки и сохранённых на Диске. Статус `delivery_pending` означает, что обработка уже завершена, осталась доставка. Старый прямой `POST /api/drive/transcripts` возвращает HTTP 409; запускайте действие через интерфейс или `POST /api/storage/action-trigger` с `actionId`.

При известной ошибке поиска, неполном покрытии или неполном аудиоблоке камера не выгружается даже как «неполный TXT»: доступные фрагменты остаются в локальном кэше. Подтверждённо полученное аудио без речи допустимо; пустой ответ регистратора и ошибка сети не являются тишиной. Ранее выгруженные неполные файлы автоматически не удаляются. Полные результаты остальных камер доставляются независимо.

Три содержательные проверки архива/неполного аудио без роста фактически обработанного аудио переводят период в `incomplete` («Требует внимания»). История сохраняется при чередовании причин и сбоях Google/DNS; сами сетевые ошибки не доказывают отсутствие записей и не увеличивают этот счётчик. Для ошибок архива действует отсрочка до истечения 24 часов после окончания периода. При одних только `INCOMPLETE_AUDIO` такой отсрочки нет. Свежие дни продолжают обрабатываться, кэш и готовые результаты сохраняются. Явный запуск кнопкой сбрасывает историю повторов выбранного периода.

XM-повтор при наличии пригодного кэша запрашивает только недостающие блоки, без прежнего предела в четыре блока; полностью новые записи обрабатываются непрерывным потоком. Проверьте свободное место одновременно для постоянной очереди и временных PCM-файлов. Подробные проверки покрытия, кэша и исходного аудио описаны в разделе диагностики `README.md`.

## PostgreSQL

Приложение подключается к PostgreSQL по настройкам `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE` из `.env`.
При старте сервер сам создает базу `PGDATABASE`, если у пользователя есть права, и инициализирует нужные таблицы.

## Email-отчёты

Получатели задаются в настройках приложения. Отчёт прикрепляется к письму как `.docx` с дневными метками, вопросом, ответом ChatGPT и обработанными камерами. Для отправки писем заполните в `.env`:

```env
REPORT_SMTP_HOST=smtp.yandex.ru
REPORT_SMTP_PORT=465
REPORT_SMTP_SECURE=true
REPORT_SMTP_STARTTLS=false
REPORT_SMTP_TIMEOUT_MS=30000
REPORT_SMTP_RETRIES=2
REPORT_SMTP_RETRY_DELAY_MS=1500
REPORT_SMTP_FALLBACK_587=true
REPORT_SMTP_USER=mailbox@yandex.ru
REPORT_SMTP_PASSWORD=app-password
REPORT_SMTP_FROM=mailbox@yandex.ru
```

## Проверка

```bash
curl http://localhost:37841/api/health
curl http://localhost:37841/api/storage
```

`/api/health` должен вернуть `ok: true`, а `/api/storage` должен вернуть данные из PostgreSQL.
