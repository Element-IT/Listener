# Camera Audio Listener

Локальное web-приложение для получения аудио с IP-камеры или NVR:

- live-аудио через RTSP;
- поиск архивных записей через XM/Xiongmai CGI, Hikvision ISAPI или Dahua CGI;
- воспроизведение аудиодорожки из архивного RTSP/XM-фрагмента;
- скачивание найденного XM/Xiongmai файла записи как сырого `.h264`;
- транскрибацию live и архивного аудио через локальную GigaAM-v3 модель;
- вопрос к OpenAI API по транскрибированному архиву выбранных групп камер;
- дневные и недельные email-отчёты с ответом ChatGPT;
- полную транскрибацию периода в TXT-файлы по камерам с загрузкой на Google Диск.

Браузер не умеет напрямую проигрывать RTSP, поэтому backend запускает `ffmpeg` и отдает странице обычный `audio/mpeg`.
Для XM/Xiongmai архивное аудио извлекается из G.711-блоков внутри `XMHead=1` потока. На этом регистраторе live RTSP отдаёт `pcm_mulaw`, поэтому архив по умолчанию декодируется как μ-law.

## Быстрый запуск

1. Скопируйте `.env.example` в `.env`.
2. В `.env` укажите пароль камеры/NVR.
3. Установите `ffmpeg`, если его нет в системе.
4. Запустите:

```powershell
npm start
```

Откройте:

```text
http://localhost:37841
```

Основной экран устроен по каналам: слева 16 кнопок каналов, справа вкладки live/архива и OpenAI API.
Названия каналов, vendor, поток, звуковой фильтр, размер блока транскрибации и часовой пояс отображения редактируются через шестерёнку в правом верхнем углу. Настройки сохраняются в браузере и PostgreSQL. Время камер задаётся как `Europe/Moscow`, а выбранное время пользователя автоматически переводится в московское перед запросом к NVR.

Можно не создавать `.env`, а запустить через переменные окружения:

```powershell
$env:CAMERA_HOST="192.168.1.100"
$env:CAMERA_USER="admin"
$env:CAMERA_PASSWORD="<пароль>"
npm start
```


## Качество звука

В настройках есть переключатель `Звук`:

- `Речь` - режим по умолчанию, срезает гул/шипение и включает мягкое FFT-шумоподавление.
- `Сильно` - более агрессивная очистка для очень шумных каналов.
- `Без обработки` - исходный звук без фильтров, полезно для сравнения.

Тот же режим можно задать в `.env` через `AUDIO_FILTER=voice`, `AUDIO_FILTER=strong` или `AUDIO_FILTER=off`. Кодек XM-архива задаётся через `XM_AUDIO_CODEC=mulaw` или `XM_AUDIO_CODEC=alaw`.

## Транскрибация

Для распознавания используется Python-пакет `gigaam`; модель по умолчанию задаётся через `GIGAAM_MODEL=v3_e2e_rnnt`.

В настройках доступен выбор восьми русскоязычных ASR-моделей GigaAM: CTC/RNNT версий v1, v2, v3 и v3 E2E. CTC подходит для приоритета скорости, RNNT - для качества распознавания слов; E2E дополнительно поддерживает пунктуацию и нормализацию чисел. Выбор сохраняется отдельно в PostgreSQL (`app_settings.transcription_model`), имеет приоритет над `.env` и применяется ко всем новым запросам, включая фоновые, без перезапуска сервера. Если PostgreSQL недоступна, сохранение завершается ошибкой и текущая модель не меняется. Во время захвата аудио, загрузки модели, распознавания или активного фонового действия переключение блокируется. Уже готовый текст не пересчитывается; ключ кеша учитывает модель.

Шкалы относительные, не являются гарантией точности или замером скорости на текущем компьютере. Скорость: архитектурная оценка CTC 5/5 и RNNT 3/5; старая версия не считается автоматически быстрее новой. Качество слов: `5 * 8.3 / средний WER`, округлённое до десятых, где 8.3% - лучший средний WER в [официальном сравнении GigaAM](https://github.com/salute-developers/GigaAM/blob/7447938d791c4f3e643386ee22c33777004293a5/evaluation.md#russian-asr). Баллы не оценивают качество пунктуации. Веса выбранной модели скачиваются при первом распознавании и затем используются из кеша; до этого в диагностике будет «Не загружена».
Страница показывает текст live под кнопкой `Стоп`, а текст выбранной архивной записи - под архивным аудио-плеером.

- live распознаётся короткими окнами, по умолчанию `TRANSCRIPTION_LIVE_SECONDS=18`;
- выбранная архивная запись тоже распознаётся блоками по 18 секунд и постепенно дописывается в текстовый блок;
- каждый архивный блок сначала извлекается в WAV, затем отправляется в GigaAM worker;
- сервер ограничивает один запрос к архиву 30 секундами (`TRANSCRIPTION_CAPTURE_CHUNK_SECONDS`, допустимо 5-60); длительный период обрабатывается последовательными блоками, готовые части сохраняются в кеше;
- фоновые действия обрабатывают до `TRANSCRIPTION_RECORDING_CONCURRENCY` архивных файлов одновременно (по умолчанию 1, допустимо 1-4), сохраняя текст в хронологическом порядке; значение `2` включайте после проверки регистратора;
- экспериментальный `TRANSCRIPTION_XM_PROGRESSIVE=true` использует одну XM login/WebSocket/FFmpeg-сессию на архивный файл и передаёт готовые PCM-блоки в GigaAM по мере загрузки; публичный блочный API остаётся резервным путём;
- при загрузке XM-архива сервер прекращает приём после нужного объёма аудио и приостанавливает поток, если ffmpeg не успевает его принять;
- результат архива кешируется в системной temp-папке, чтобы повторное открытие той же записи было быстрым;
- длинные архивы на CPU могут распознаваться заметно дольше воспроизведения.

Настройки:

```env
PYTHON_PATH=python
GIGAAM_MODEL=v3_e2e_rnnt
GIGAAM_DEVICE=auto
TRANSCRIPTION_CHUNK_SECONDS=20
TRANSCRIPTION_LIVE_SECONDS=18
TRANSCRIPTION_CAPTURE_CHUNK_SECONDS=30
TRANSCRIPTION_RECORDING_CONCURRENCY=1
TRANSCRIPTION_XM_PROGRESSIVE=false
TRANSCRIPTION_ARCHIVE_MAX_SECONDS=0
```

`TRANSCRIPTION_ARCHIVE_MAX_SECONDS=0` означает без ограничения длительности архива.
Это не отменяет ограничение одного блока: API `/api/recordings/transcript` возвращает одну часть, следующий запрос должен увеличивать `offsetSeconds` на полученное `durationSeconds` до конца периода.

При запуске сервер проверяет Python, импорт GigaAM/PyTorch, доступность CUDA и выполнение небольшого вычисления на выбранной GPU. `GIGAAM_DEVICE=auto` выбирает CUDA после успешной проверки, иначе CPU; `cpu` принудительно использует процессор. При явном `cuda` или `cuda:N` недоступность выбранной GPU считается ошибкой, без незаметного перехода на CPU.

В настройках блок «Транскрибация» показывает выбранное устройство, а после загрузки модели - фактическое устройство её параметров. Также доступны состояние модели, версия PyTorch/CUDA, название NVIDIA GPU, видеопамять и драйвер. Данные обновляются каждые 5 секунд, пока настройки открыты. До первой транскрибации состояние «Не загружена» нормально: модель загружается по первому запросу. Диагностика доступна в `/api/health` и `/api/transcription/status`.

Если NVIDIA GPU найдена, но текущий Python не использует CUDA, сервер автоматически готовит отдельное окружение с PyTorch/TorchAudio `2.11.0+cu128` и GigaAM из `requirements.txt`. Для этой сборки автоподготовка требует NVIDIA-драйвер Windows >=570.65 или Linux >=570.26; системный CUDA Toolkit не переустанавливается. Уже работающая CUDA-сборка из `PYTHON_PATH` также подходит. Без GPU используется рабочий CPU-интерпретатор, а если зависимости отсутствуют, создаётся отдельная CPU-сборка. Системный Python не изменяется.

GigaAM 0.2.0 закреплён в `requirements.txt` на официальном GitHub-коммите `7447938d791c4f3e643386ee22c33777004293a5`: эта версия пока не опубликована в PyPI.

Пакеты скачиваются только при необходимости, из официального индекса PyTorch, репозитория GigaAM и PyPI. На следующих стартах окружение повторно проверяется и переиспользуется без установки. До окончания подготовки планировщик не запускается, запросы транскрибации получают HTTP 503, а в настройках виден текущий этап. При сбое загрузки или установки рабочая CPU-сборка сохраняется, причина показывается в настройках. Веса модели по-прежнему загружаются только при первой транскрибации.

```env
GIGAAM_AUTO_INSTALL=true
# По умолчанию окружения находятся в .runtime/python.
# Для CUDA рекомендуется минимум 12 ГБ свободного места на диске установки.
# GIGAAM_RUNTIME_DIR=D:/ListenerRuntime
# Необязательный HTTP-прокси только для скачивания Python-пакетов:
# GIGAAM_PIP_PROXY=http://127.0.0.1:1080
# Для прямой загрузки пакетов без системного прокси: GIGAAM_PIP_PROXY=direct
```

`GIGAAM_AUTO_INSTALL=false` запрещает скачивание и установку, но позволяет использовать уже подготовленное окружение. Подробности установки записываются в `install.log` внутри `GIGAAM_RUNTIME_DIR`. Окружения и локальные настройки не включаются в Git; на другом сервере окружение будет подготовлено заново. Для установки без веб-сервера: `python scripts/prepare_transcription.py --runtime-dir .runtime/python --device auto`.

## Транскрибация аудиофайлов

Вкладка **Аудиофайлы** принимает несколько файлов (выбор или перетаскивание): MP3, WAV, M4A, AAC, OGG, OPUS, FLAC, WMA, AIFF, AMR и другие поддерживаемые FFmpeg аудиоформаты. Максимум — 2 ГБ на файл. Нажмите **Транскрибировать**: файлы обрабатываются последовательно выбранной в настройках моделью GigaAM и с текущим фильтром звука, без обращения к камерам, OpenAI или Google Диску.

Из окончания имени `-YYYYMMDD-HHMMSS` берётся начало записи: `1-recording-20261009-142239.mp3` → `09.10.2026 14:22:39`. К этому времени прибавляется смещение каждого распознанного фрагмента, включая переход через полночь. Время из имени считается местным в выбранном часовом поясе и не сдвигается относительно московского времени камер. Если дата отсутствует или некорректна, используются относительные тайминги от `00:00:00`.

Кнопка **Скачать единый TXT** объединяет результаты по файлам: сначала по дате из имени, затем файлы без даты в порядке выбора. В каждом разделе указаны имя файла, модель и тайминги. Текст появляется по мере распознавания; частичный TXT доступен ещё до завершения. Ошибка одного файла не останавливает остальные, но отмечается в TXT как неполный результат. **Стоп** сохраняет уже полученный текст. Оставляйте страницу открытой до завершения и скачивайте результат перед её закрытием. Временные аудиофайлы сервер удаляет после обработки или отмены.

## OpenAI API

Во вкладке `OpenAI API` можно создать группы камер с периодами, сохранить действия и запускать их вручную. Для действия доступны режимы `daily`, `weekly` и `once`, а результат выбирается отдельно: email-отчёт OpenAI или полная транскрибация в TXT на Google Диск. Для варианта Google Диска вопрос и ключ OpenAI не нужны.

Для режимов `daily` и `weekly` сервер сам проверяет расписание каждые `ACTION_SCHEDULER_INTERVAL_SECONDS` секунд и запускает действие после окончания выбранного периода группы. Используются явные IANA-зоны: `CAMERA_TIME_ZONE=Europe/Moscow`, `DISPLAY_TIME_ZONE=Asia/Yekaterinburg`. Москва — UTC+3, Екатеринбург — UTC+5, поэтому выбранные в интерфейсе `13:00` превращаются для камеры в `11:00`.

Дневной и недельный отчёты выполняются независимо. Дневной отчёт отправляется после соответствующего дневного запуска. Для режима `вчера` с выключенными выходными понедельник использует предыдущую пятницу. Недельный отчёт охватывает рабочую неделю с понедельника по пятницу и становится доступен после 18:00 пятницы либо после более позднего окончания пятничной группы; если пятничная отправка была пропущена, планировщик может выполнить её в субботу. Галочка `Обрабатывать записи в выходные` управляет дневными запусками по субботам и воскресеньям.

Временные ошибки камер и транскрибации повторяются с увеличивающейся паузой от 1 до 60 минут. Неудачный период сохраняется для повтора после смены даты в течение `ACTION_SCHEDULER_RETRY_MAX_AGE_HOURS` часов (по умолчанию 168). Свежие завершённые периоды имеют приоритет перед старыми повторами. Ошибка отдельного архивного файла не отменяет обработку остальных камер; для Google Диска камера с известной ошибкой не выгружается даже с пометкой неполноты.

Кнопка `Запустить` у планового действия, а также у любого действия Google Диска, включая `once`, ставит работу в серверную фоновую очередь: вкладку браузера после этого можно закрыть. В карточке сразу отображается состояние `В очереди` или `Выполняется`; повторное нажатие не запускает второй экземпляр того же периода. Разовый email-сценарий по-прежнему выполняется через открытую страницу.

Карточка показывает обратный отсчёт до следующего фонового запуска с учётом часового пояса сервера, выходных и повторов после ошибки. Отсчёт обновляется каждую секунду, состояние с сервера - каждые 3 секунды. Во время работы отображаются этап, камера, интервал, число готовых частей и прогресс. Подготовка и транскрибация занимают 0-90% шкалы, затем идут запрос OpenAI и отправка отчёта; 100% означает завершение действия.

Во время фонового запуска кнопки запуска, изменения и удаления заменяются кнопкой `Остановить`. Остановка отменяет загрузку и распознавание текущего блока или запрос OpenAI, сохраняет готовые части и не вызывает письмо об ошибке. Если письмо уже отправляется, приложение дожидается результата SMTP: принятое почтовым сервером письмо отозвать нельзя. Остановленный период автоматически не повторяется, следующие периоды продолжают выполняться по расписанию. Повтор того же периода можно поставить вручную кнопкой `Запустить`.

После запуска действия приложение:

1. ищет архивные записи по каждой камере из выбранных групп;
2. транскрибирует найденный период тем же GigaAM-пайплайном, что и основная вкладка;
3. показывает накопленный текст, статус и прогресс;
4. отправляет вопрос и транскрипт в OpenAI API;
5. показывает ответ ChatGPT;
6. отправляет email-отчёты, если они включены в действии.

Для результата `Google Диск` пункты 4–6 заменяются сохранением и доставкой: после полной обработки камеры сервер надёжно сохраняет локальные данные для одного UTF-8 `.txt`, затем отдельная очередь доставки отправляет его в дочернюю папку вида `2 Бухгалтерия`. В начале TXT указаны номер и подпись камеры, далее строки вида `[начало–конец] текст`. Завершённая камера не ждёт окончания других камер. Поиск существующих файлов на Диске ограничен по времени: недоступность Google не блокирует получение архива и транскрибацию.

Если поиск записей или распознавание хотя бы одной части камеры завершились ошибкой, её промежуточные результаты остаются в локальном кэше. Неполный TXT не создаётся для загрузки и не отправляется на Диск. Полностью полученное и обработанное аудио без распознанной речи считается корректным результатом; нулевой ответ регистратора или сетевой сбой не считаются тишиной. Полные результаты других камер продолжают сохраняться и отправляться. Файлы, ранее выгруженные старыми версиями с пометкой `НЕПОЛНАЯ ТРАНСКРИБАЦИЯ`, автоматически не удаляются и не считаются подтверждением полной обработки.

Очередь доставки хранится в `.runtime/drive-outbox`: JSON-записи содержат готовый транскрипт, параметры формирования файла и подтверждение доставки с ID файла Google Диска. При перезапуске приложение использует эти записи, пропуская уже готовые камеры до поиска архива и чтения их блочного кэша. Сбой Google повторяет только отправку с паузой от 1 до 60 минут, без нового скачивания аудио или запуска ASR. Карточка различает файлы на компьютере, ожидающие отправки и подтверждённые файлы на Диске; статус `delivery_pending` означает «Транскрибация готова — ожидает отправки».

Не удаляйте `.runtime/drive-outbox` как временный кэш и включайте её в резервную копию вместе с PostgreSQL. Содержимое включает текст разговоров: ограничьте доступ и не добавляйте очередь в Git. Старый прямой `POST /api/drive/transcripts` закрыт ответом HTTP 409; для ручного запуска используйте кнопку действия или `/api/storage/action-trigger`, чтобы не обходить проверку полноты и локальную очередь.

Автоматическая обработка по-прежнему начинается после окончания выбранного периода. Предварительная почасовая загрузка архива в течение дня не включена.

Ключ не хранится во фронтенде. Укажите его в `.env` или переменных окружения:

```env
OPENAI_API_KEY=sk-proj-...
OPENAI_MODEL=gpt-5.6-terra
OPENAI_MAX_OUTPUT_TOKENS=1200
OPENAI_TIMEOUT_MS=120000
```

Для подключения через vpnxxx добавьте в `.env` и перезапустите приложение:

```env
OPENAI_PROXY_URL=vpnxxx://auto
```

В режиме `vpnxxx://auto` приложение перед каждым запросом OpenAI читает `%APPDATA%\vpnxxx\temp\privoxy.conf` (с запасным путём через `%USERPROFILE%`) и использует локальный `listen-address`; если указаны IPv4 и IPv6, их порты должны совпадать. Поэтому смена динамического HTTP-порта после перезапуска vpnxxx не требует перезапуска Listener. SOCKS-порт vpnxxx напрямую не поддерживается.

Для другого прокси укажите полный URL HTTP(S)-прокси с CONNECT, например `OPENAI_PROXY_URL=http://127.0.0.1:8118`; URL с логином и паролем также поддерживается. TLS-проверка сертификата OpenAI остаётся включённой. Настройка применяется только к OpenAI, в ручных и фоновых действиях; камеры, PostgreSQL и SMTP её не используют. Прокси должен работать на том компьютере, где запущен Node.js. При переносе на VPS укажите доступный там адрес прокси или удалите настройку для прямого подключения. Системный прокси Windows автоматически не подхватывается.

Если прокси недоступен, запрос завершается ошибкой без перехода на прямое соединение. Таймаут возвращается как HTTP 504, остановка пользователем - как HTTP 499. `/api/config` показывает признак `openAi.proxyEnabled`, не раскрывая адрес или учётные данные прокси.

## Email-отчёты

Получатели задаются в настройках приложения в поле `Почты для отчётов`. SMTP-параметры задаются в `.env` или переменных окружения:

При ошибке фонового действия на эти же адреса отправляется отдельное письмо с названием действия, вопросом, этапом, периодом, камерой, количеством обработанных частей и текстом ошибки. Это уведомление не зависит от галочек дневного и недельного отчётов. Ошибки отдельных записей также вызывают письмо о неполной обработке. Если отправка уведомления не удалась, её ошибка сохраняется в результате действия и показывается в карточке. Недоступный SMTP не сможет доставить и уведомление об ошибке SMTP. Адреса из настроек имеют приоритет; `REPORT_EMAIL_TO` используется, когда список в настройках пуст.

REPORT_SMTP_STARTTLS=false
REPORT_SMTP_TIMEOUT_MS=30000

REPORT_SMTP_USER=mailbox@yandex.ru

В диалоге действия чекбоксы `Отправлять отчёт за день` и `Отправлять отчёт за неделю` видны для режимов `daily` и `weekly`. Если отмечены оба, дневное письмо отправляется после дневного запуска, а недельное — отдельным письмом только в конце рабочей недели. Письмо содержит короткое описание, а сам отчёт прикрепляется как `.docx`: внутри есть период, вопрос, ответ ChatGPT, метки по дням, обработанные камеры и подгруженный текст.

## Google Диск

Одна ссылка на папку не является токеном и не даёт серверу право записи. Для обычной папки в «Моём диске», включая указанную папку `1yaqWNPjJtPKWnfGUEQxZ2kkB_bv0sYSU`, нужны OAuth 2.0 данные Google-аккаунта с правом редактора:

```env
GOOGLE_DRIVE_ROOT_FOLDER_ID=1yaqWNPjJtPKWnfGUEQxZ2kkB_bv0sYSU
GOOGLE_DRIVE_AUTH_TYPE=oauth
GOOGLE_DRIVE_CLIENT_ID=...
GOOGLE_DRIVE_CLIENT_SECRET=...
GOOGLE_DRIVE_REFRESH_TOKEN=...
```

`refresh_token` получается один раз при OAuth-авторизации с доступом `offline`; для записи по ID в уже существующую папку нужно запросить scope `https://www.googleapis.com/auth/drive`. Сервер сам обменивает refresh token на короткоживущие access token и обновляет их в фоне. Секреты хранятся только в `.env`/переменных окружения и не должны попадать в Git.

Сервисный аккаунт допустим только если целевая папка находится в Shared Drive Google Workspace. Тогда Shared Drive нужно предоставить `client_email` с ролью не ниже Contributor и задать `GOOGLE_DRIVE_SERVICE_ACCOUNT_EMAIL` и `GOOGLE_DRIVE_SERVICE_ACCOUNT_PRIVATE_KEY`. Для обычного «Моего диска» сервисный аккаунт не подходит, потому что у него нет собственной квоты Drive.

## Диагностика и восстановление фоновой транскрибации

Для расследования сбоя сначала открывайте «Диагностика по камерам» в карточке действия. Дата запуска и обрабатываемый период показываются отдельно: повтор сегодня может относиться к старому архиву.

План проверки нестабильного запуска:

1. Зафиксировать `runKey`, период, модель и фактическое устройство из `/api/transcription/status`; состояние и покамерные результаты доступны в `/api/storage/action-status`. Не публиковать `.env`, токены и содержимое разговоров.
2. Проверить поиск за **тот же период и канал**. `searchOutcome=found` означает найденные записи, `confirmed_empty` — подтверждённый пустой ответ, `unconfirmed` — неоднозначный ответ регистратора. Ошибка HTTP/сети резервного поиска не должна превращаться в «записей нет».
3. Сравнить объединение интервалов найденных записей с запрошенным периодом. В диагностике сохраняются точные пропуски и длительности; один час архива нельзя считать обработкой десяти часов. Время без распознанной речи считается обработанным только при подтверждённой длительности аудио.
4. Разделить получение аудио, ASR и доставку. Диагностика хранит время поиска, обработки, получения аудио, распознавания, количество блоков кэша, ошибки и пропуски по камерам. Время получения/ASR суммируется по блокам и при параллельной обработке может отличаться от общего времени.
5. Проверить возобновление: камеры с полным результатом в локальной очереди или подтверждённым полным файлом на Диске пропускаются до поиска/загрузки архива и чтения блочного кэша. Для незавершённой камеры полный кэш используется повторно, запрашиваются только недостающие блоки. Короткий/неполный блок не подтверждает оставшийся период. Новые блоки кэша содержат версию и источник записи; старый кэш без источника нельзя безопасно объединять только по дате.
6. Проверить доставку отдельно: готовая камера сохраняется локально и передаётся отдельной очереди, даже если другая камера завершилась ошибкой. Информационное предупреждение об успешном резервном поиске не запрещает выгрузку. Ошибки Google сохраняют готовый результат и повторяют только доставку; неполные камеры не выгружаются. Проверить JSON-запись и подтверждение доставки в `.runtime/drive-outbox`, не публикуя содержимое транскрипта.
7. Запустить `node --test`, затем короткую реальную проверку аудио и проверить состояние после перезапуска. Длительный ежедневный прогон оценивается отдельно: успешный короткий тест не доказывает обработку всех камер за день.

Три содержательные проверки без реального продвижения переводят **этот период** в «Требует внимания» (`incomplete`) без дальнейших автоповторов обработки. Учитываются подтверждённые ошибки покрытия архива и неполного аудио, в том числе их смешанные наборы; смена камеры или кода ошибки сама по себе не считается прогрессом. Если среди причин есть недоступный/неполный архив, остановка повторов разрешена только через 24 часа после окончания периода, чтобы дать регистратору время обновить индекс. Готовые файлы, очередь доставки и кэш сохраняются; свежие периоды продолжают выполняться. Кнопка «Запустить» позволяет явно повторить период и сбрасывает историю повторов.

При одних только `INCOMPLETE_AUDIO` возраст периода не ограничивает остановку после трёх проверок без прогресса. Прогресс измеряется фактически обработанной длительностью по камерам/интервалам и увеличением полученного аудио в том же проблемном блоке; повторное чтение того же кэша или отправка TXT не являются новым прогрессом транскрибации. Разброс длительности до 0,25 с не обнуляет серию. Сетевые/DNS-сбои, ошибки Google, декодера или модели не превращаются в отсутствие архива и не увеличивают этот счётчик, но сохраняют уже накопленную историю вместо её обнуления.

Если у записи уже есть пригодные блоки кэша, XM-повтор сохраняет их и адресно запрашивает только недостающие блоки независимо от их числа; прежнего ограничения в четыре блока нет. Каждый запрос содержит до 60 с звука с прогревом фильтра до 10 с и поправкой на целосекундный seek регистратора. Если прогретый запрос короче ожидаемого, выполняется один прямой запрос блока. Для новой записи без пригодного кэша сохраняется непрерывный потоковый режим. Результаты адресной обработки имеют отдельные ключи `xm-targeted-pcm-v2` с фактической точкой начала и величиной отброшенного прогрева; завершённый старый кэш не перезаписывается. Проверяются все ожидаемые исходные G.711-байты; допуск 0,05 с относится только к завершению декодера/фильтра, а не к отсутствующим исходным байтам.

Нулевой ответ, `State=End`, закрытие соединения и повторный одинаковый недобор **не подтверждают отсутствие аудио в исходном архиве**. При таких ошибках доступные фрагменты остаются локально; неполный TXT не выгружается, даже если соседняя запись тоже не содержит полученных байтов. Полностью полученная и обработанная тишина с пустым результатом ASR допустима. Текущий XM-демультиплексор не восстанавливает временную шкалу всех кадров: вычисленные границы недобора являются диагностической оценкой, а не доказанным местоположением пропущенной речи. Автоматический пропуск отсутствующего участка без независимого подтверждения не выполняется.

Кэш не заменяет отсутствующий исходный архив: если в нём есть только часть дня, полного отчёта из него получить нельзя. Подтверждение причины удаления или срока хранения требует проверки настроек самого регистратора.

Потоковый XM-режим непрерывно принимает и декодирует аудио в ограниченный временный PCM-файл, а модель читает из него готовые блоки параллельно загрузке. Это отделяет скорость получения от пауз распознавания, не требует держать весь архив в RAM и не задерживает первый блок до конца записи. Для одного часа моно PCM 16 кГц требуется до 115,2 МБ временного места на одну одновременно обрабатываемую запись. Файл удаляется после завершения/ошибки/отмены; уже записанный кэш транскрипта сохраняется. Принудительное завершение процесса может оставить временный файл, поэтому свободное место также важно проверять.

## Важные ограничения

- Аудио из старых записей появится только если камера/NVR уже записывали аудиодорожку в тот момент.
- У камеры должен быть микрофон или аудиовход.
- Для офиса проверьте законность записи звука и уведомление сотрудников/посетителей.
- Не публикуйте это приложение в интернет без авторизации, HTTPS и ограничения доступа.
